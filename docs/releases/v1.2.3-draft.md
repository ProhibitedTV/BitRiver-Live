# BitRiver Live v1.2.3 draft release notes

Status: stable-line draft. Public prerelease
[`v1.2.3-rc.13`](https://github.com/ProhibitedTV/BitRiver-Live/releases/tag/v1.2.3-rc.13)
is available for operator evaluation, but clean-host XOA/NPM/reboot and repeated
OME recovery evidence are still required before stable `v1.2.3` promotion.
RC13 carries the signed release-set root required by the promotion transaction;
it is eligible for evidence gathering but remains blocked from stable promotion
until all eight external gates bind to that exact root hash.

## Summary

BitRiver Live packages the core pieces of a self-hosted live-streaming stack into one repository and one deployment contract:

- Go API and admin control plane
- Next.js viewer
- SRS ingest
- OvenMediaEngine playback
- FFmpeg-based transcoding
- Postgres and Redis
- Compose-based deployment assets, installers, and release automation

This release focuses on making that stack approachable and trustworthy for public adopters: cleaner repo hygiene, clearer onboarding, explicit support boundaries, and a more complete contribution and release surface.

## What operators get

- A documented single-host deployment baseline centered on `deploy/docker-compose.yml`
- Quickstart and smoke-test flows from the same source tree
- A production golden-path gate that publishes deterministic 1080p RTMP,
  decodes OME and transcoder playback, exercises chat/moderation and VOD, checks
  aggregate health, scans its evidence, and tears down
- Source-free Linux launcher archives and amd64/arm64 `.deb`/`.rpm` packages assembled from one canonical asset manifest
- An Ubuntu systemd host manager that stages the Compose stack under `/opt/bitriver-live`, keeps configuration/data separate, and never activates sample credentials
- Release artifacts for binaries, Cosign-bundled launcher binaries, viewer
  bundle, and version-matched container images, including the OME config helper
- Candidate-only builds with a signed manifest covering every public artifact,
  five exact image digests/signatures, SBOMs, dependency pins, and sanitized
  contract/product/scan evidence
- A protected, environment-reviewed stable workflow that copies candidate
  bytes, retags exact digests, publishes through a draft, emits signed rollback
  metadata, and supports append-only candidate revocation without rebuilding
- Five first-party images under `ghcr.io/prohibitedtv`, published under the
  exact candidate tag and checked for anonymous access before the GitHub
  prerelease is created
- Supporting runbooks for security, upgrades, monitoring, and production release execution

## Known limits

- The supported baseline is still operator-managed single-host deployment.
- HA or multi-host guarantees are not part of this release.
- Kubernetes is not the primary deployment path in this repository.
- Operators still own host hardening, secret rotation, backups, and capacity planning.
- Ubuntu Server 24.04 LTS on amd64 is the production installation target. Debian 12, RPM hosts, arm64, and XOA reboot recovery remain provisional until tagged clean-host evidence is attached.
- Source-built canonical Compose has automated real RTMP, OME/transcoder
  decode, chat/moderation, VOD, and aggregate-health proof. The tag workflow
  repeats that gate from the five published, digest-pinned first-party images.
  Clean-host Ubuntu installation, Nginx Proxy Manager playback, authenticated
  OME control, reboot recovery, and browser recovery/quality behavior still
  require their own evidence before stable promotion.

## Recommended upgrade / rollout notes

1. Validate your target environment with `deploy/check-env.sh`.
2. Follow [`docs/production-release.md`](../production-release.md) before tagging or rolling out.
3. Confirm release notes, checksums, image digests, and the changelog agree on
   the exact immutable tag. Never move a failed RC tag; fix the source and
   increment the candidate number.
4. Run `scripts/test-production-golden-path.sh --stack running --client docker`
   against the deliberately prepared release-candidate installation and retain
   its sanitized JSON report.
5. Run `scripts/test-stateful-upgrade.sh` and retain its secret-scanned JSON
   report. The current RC19-to-RC20 result proves database/migration-layer
   in-place compatibility only; complete exact-image Compose/config rollback,
   interrupted deploy, and post-upgrade golden-path evidence before promotion.
6. Install only the published artifacts on a clean Ubuntu 24.04 amd64 VM, reboot it, and record authenticated OME plus real ingest/playback evidence before announcing production readiness.
7. Bind all eight required gate artifacts to the same candidate manifest hash
   in a reviewed `docs/releases/promotions/` record. Dispatch stable promotion
   only after the live issues are closed; keep `publish_latest` false unless
   moving convenience aliases is an explicit rollout decision.
