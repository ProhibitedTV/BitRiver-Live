## Current scope - viewer compatibility matrix (#1307) (2026-09-12)

- Turn the existing single-project Playwright suite into an explicit browser/device qualification contract for the supported viewer without changing product behavior merely to make tests pass.
- Preserve one full Chromium desktop regression project as the broad baseline, then add a smaller release-critical matrix across Chromium, Firefox, WebKit, Android/Chrome emulation, and iPhone/WebKit emulation. Reuse existing channel/chat/playback, auth/navigation, creator setup, mobile overflow, and accessibility tests rather than building a parallel fake viewer.
- Separate engine/device support from protocol support. Mocked browser tests can prove layout, navigation, auth/cookie behavior, chat UI/reconnect presentation, player fallback/error states, and creator flows; real HLS/LL-HLS/WebRTC decode evidence remains owned by the production golden path and must not be inferred from mocked routes.
- Keep retry policy honest: do not add broad retries to turn browser-specific failures green. Any unsupported engine behavior must be fixed, narrowly excluded with documented rationale, or surfaced as a release blocker.
- Publish a support matrix that names the tested desktop/mobile projects, which critical flows run on each, browser-version policy, media/protocol caveats, and the boundary between CI emulation and real device/Safari evidence.
- Keep the release feature freeze intact: this slice may make compatibility fixes required by the declared baseline, but it does not add 4K support, new media protocols, or unrelated viewer features.

### Risks and test boundaries

- Running every existing browser test five times would be expensive and can obscure engine-specific failures behind unrelated coverage. Preserve the current complete suite on Chromium and define one focused compatibility spec set that runs on all five projects.
- Playwright's mobile presets can change user agent, viewport, touch, and device scale behavior. Ensure project-level emulation does not fight tests that intentionally resize through several narrow widths; mobile critical coverage should assert touch-capable behavior and no document overflow without hard-coding one device-only layout.
- HLS support differs by browser engine. Tests must distinguish native HLS, hls.js fallback, and unsupported/mock-only behavior instead of pretending a successful mocked playlist proves decoder support.
- WebKit on Linux is Safari-equivalent engine coverage, not a claim that current macOS/iOS Safari hardware was exercised. Documentation must state that boundary explicitly.
- The permanent CI path should install only browsers actually required by the matrix and retain one production standalone build/server boundary. Avoid duplicate Next builds per project.

### Test and rollout plan

- Add named Playwright projects for Chromium desktop, Firefox desktop, WebKit desktop, Android/Chrome emulation, and iPhone/WebKit emulation using Playwright's maintained device descriptors where appropriate.
- Add/retag a compact critical compatibility suite covering channel watch/playback recovery presentation, authentication/navigation, chat, creator setup, accessibility, mobile/touch interaction, and horizontal-overflow refusal.
- Add static repository contract tests for the project names, browser engines/device presets, no blanket retry policy, and expected critical/full-suite split.

- Run clean npm install, zero-high audit, strict lint, Jest, all critical projects, full Chromium integration, production build, literal `./scripts/verify.sh --viewer`, protected viewer CI, automated review, and the aggregate Merge gate before squash merge.
- Keep #1307 open if real-media engine-class evidence or real Safari/device evidence remains unproven after this repository-side matrix lands.
